# First-version contract

Rust Axum server, MySQL 8.4 persistence, Solid 2 SPA. API JSON uses snake_case.

## Models

- Field: `{name, label, kind: "text" | "textarea" | "url", required: boolean}`
- Component: `{id, name, description, renderer: "hero" | "text" | "callout" | "cards" | "external", fields: Field[]}`. External components render in the consuming app by component ID; the CMS displays a labelled field-value preview and executes no external code.
- Region: `{name, allowed_components: string[], max_components: number}`. Maximum is positive. An empty allowed list permits no components.
- Template: `{id, name, description, regions: Region[]}`
- Block: `{id, component_id, region, fields: Record<string,string>}`
- Page: `{id, title, slug, aliases: string[], template_id, blocks: Block[], revision: number, published_revision: number | null}`. Slugs and aliases are case-sensitive absolute paths such as `/` and `/about`, at most 2048 bytes. Missing aliases deserialize as an empty list for older stored data and API clients.
- Bootstrap: `{pages: Page[], templates: Template[], components: Component[], access: Access, reviews: Review[]}`. Pages are filtered to current grants; reviews require access to both submitted and current paths.
- Access: `{id: string, role: "admin" | "reviewer" | "editor", paths: string[]}`. Paths are effective individual plus group grants. Admin and reviewer have all-page access regardless of paths.
- Member: `{id, name, role, paths: string[], groups: string[]}`. ID is the username for built-in accounts, or the stable provider user ID for custom providers. No email matching or external invitations. Organization JSON never contains passwords.
- Group: `{id, name, paths: string[]}`.
- Organization: `{revision: number, members: Member[], groups: Group[]}`. One installation, one organization.
- Review: `{id: page_id, submission_id: UUID, content: {page, template, components}, submitted_by: user_id, status: "submitted" | "changes_requested" | "approved", feedback: string, reviewed_by: user_id | null}`. One latest review per page, not an audit log.

## API

All `/api/admin/*` require a signed-in session and local membership. Unknown authenticated identities return 403, not automatic membership. Errors are `{error: string}` with suitable HTTP status. Unknown IDs return 404. Mutations validate references and rules before persistence. Authorization reads and changes run together under the database lock; revoking membership or grants takes effect on the next operation.

Admin has all permissions. Reviewer can read/edit every draft and approve or request changes, but cannot manage members, mutate templates/components, delete pages, or publish directly. Editor can read/create/edit/move/submit pages only within individual or group grants. Grants include the exact path and segment-aware descendants, never lexical prefixes. Moves check every old/new descendant path as well as the moved page. Grants remain at their configured paths after moves. All known members can read definitions for authoring. Public content reads only published snapshots and needs no membership.

- `GET /api/auth/config` returns `{method: "password"}` for built-in accounts. Custom providers may return `{method: "redirect", label: string}`; the login UI then navigates to `GET /api/login`, and a failed sign-in may return to `/admin?auth_error=1`. It never returns secrets. Login UI waits for this response and shows an error with retry if it fails. The Account screen and Organization password fields appear only for `password`.
- `POST /api/login` with `{username, password}` returns 204 and sets an HttpOnly SameSite=Strict session cookie. Wrong or unknown credentials return 401 with the same message. After 5 failures for one username within 15 minutes, attempts for it return 429 until the window passes.
- `POST /api/logout` deletes the session and clears the cookie, returning 204. Custom providers may instead return `{redirect_url: string}`; the frontend navigates there to end a hosted session.
- `POST /api/account/password` with `{current_password, password}` changes the signed-in member's password. A wrong current password returns 403. Success ends all of that account's sessions and returns 204 with a new session cookie.
- `PUT /api/admin/members/{id}/password` admin only, with `{password}` sets a member's password and ends their sessions. Returns 204, or 404 when no member has that ID. Passwords need 8 to 1024 characters; others return 400.
- `GET /api/admin/bootstrap` returns Bootstrap.
- `POST /api/admin/pages` with `{title, slug, template_id}` returns Page, 201, empty blocks and revision 1.
- `PUT /api/admin/pages/{id}` with full Page updates draft and returns Page. Require matching revision, increment on save; stale writes return 409. Changing template must validate all blocks. A changed slug atomically moves all descendants by path-segment prefix and increments their revisions too. Reject root moves, moves into the same subtree, invalid descendant paths, and destination collisions. Published snapshots remain unchanged. Reload bootstrap after a move.
- `POST /api/admin/pages/{id}/publish` admin only, with `{revision}` validates and snapshots saved draft, returns Page. Stale revision returns 409. Snapshot slug conflicts roll back, never overwrite another page's snapshot.
- `POST /api/admin/pages/{id}/submit` with `{revision}` validates the saved page and stores an exact page/template/used-component snapshot. Returns Review with a new submission_id and submitted status. Replaces any previous review. Stale revision returns 409.
- `POST /api/admin/reviews/{page_id}` admin/reviewer only, with `{revision, submission_id, approve: boolean, feedback: string}` returns Review. Requires pending status, exact submission ID and revision, and equality between the current page/schema and submitted snapshot. Changed drafts, moves, imports, schema edits or resubmissions make old approvals return 409. `approve:true` atomically publishes and marks approved. `approve:false` requires nonempty feedback and marks changes_requested. No separate later publication step. Reviewers may approve their own submissions.
- `GET /api/admin/organization` admin only, returns Organization.
- `PUT /api/admin/organization` admin only, accepts the full Organization with matching revision and returns the next revision. Stale updates return 409. Validates unique member/group IDs, required names, canonical paths, and group references. Removing a group requires removing its member references. Once a local admin exists, at least one must remain. Removing a member deletes their password and sessions and denies future operations.
- `DELETE /api/admin/pages/{id}` admin only, returns 204. Returns 409 if any descendant draft remains; no recursive deletion. Deletes its snapshot and review.
- `POST /api/admin/templates` with Template excluding id returns Template, 201.
- `PUT /api/admin/templates/{id}` with Template validates existing drafts and returns Template. Reject changes that invalidate existing pages. Published snapshots remain unchanged.
- `POST /api/admin/components` with Component excluding id returns Component, 201.
- `PUT /api/admin/components/{id}` with Component validates existing drafts and returns Component. Reject changes that invalidate existing pages. Published snapshots remain unchanged.
- `GET /api/admin/package?path=/news` admin only, returns `application/zip` with `Content-Disposition: attachment`. Contains the page at that path and all descendants (`/` exports every page), plus the templates they use and the components those templates allow or their blocks place, in the Local serialization file format. 400 when no page is at or below the path.
- `POST /api/admin/package` admin only, with a zip body in the same layout. Returns `{created, updated, unchanged, components_added, templates_added}`; page lists hold paths. See Content packages.
- `DELETE /api/admin/templates/{id}` and `DELETE /api/admin/components/{id}` admin only, return 204. 409 names the users when a page draft uses the template, or a template allows or a page draft uses the component. Published snapshots and reviews keep their own copies. 404 for unknown IDs.
- `GET /api/content?slug=/about` public, returns `{page, template, components}` from immutable published snapshot, 404 for unpublished.
- `GET /health` returns 200 when the database is accessible, 500 on database failure.

Aliases are exact paths, not subtree mappings. Editors change them through the full Page draft update, with the same revision and review workflow as content. Adding or removing an alias requires access to that alias path; unchanged aliases outside an editor's grants may remain during content edits. Reject unsafe/reserved paths, duplicates, self-redirects, collisions with draft page paths or aliases, and paths used by another page's published aliases. Draft aliases also cannot claim another page's published canonical path. Conflicts return 409; invalid paths or duplicate/self aliases return 400. CLI imports enforce the same path rules.

Publication atomically replaces the page's live aliases together with its snapshot. Public `GET` and `HEAD` requests to a published alias return `301 Moved Permanently` with a relative `Location` pointing directly to that page's published slug, preserving the query string. No redirect for other methods. Draft edits and moves leave live redirects unchanged until publication; removing aliases requires publishing, while deleting the page removes its aliases immediately. The published slug remains canonical and visible in the browser. Alias targets cannot form chains or loops. Existing 301 responses may remain in browser/search-engine caches after changes. Content APIs still require the canonical slug; their published Page JSON includes aliases so a headless frontend can implement its own redirects.

Server serves frontend dist with SPA fallback. Editor path `/admin`; other paths render public pages. Frontend Vite proxy `/api` and `/health` to port 3000. `BADDIE_BIND` overrides the listener; otherwise `PORT` binds `0.0.0.0:$PORT`, or `127.0.0.1:3000` if absent. `DATABASE_URL` is a required MySQL connection URL; `BADDIE_STATIC` defaults `web/dist`. Tables use InnoDB. Admin and CLI operations use a shared lock row to serialize authorization, validation and writes across connections. Public snapshot reads and health checks use ordinary connections without that lock and never read uncommitted changes. The server admits at most 16 database jobs per AppState, returning 503 when full. A cancelled request retains its slot until its blocking job finishes. Sessions are stored in MySQL; failed sign-in counters are per process.

Seed idempotently on a new database: hero with eyebrow/title/body/button_label/button_url, text with title/body, callout with title/body/button_label/button_url, cards with title/body. Required title; other fields optional. Homepage template with main region allowing all components, maximum 20. Home page draft with hero and text, suitable editorial starter copy. IDs are arbitrary strings, frontend must discover them.

## Headless integration

The server optionally accepts two independent installation-wide server-to-server keys, configured through `BADDIE_CONTENT_API_KEY` and `BADDIE_COMPONENT_API_KEY`. Missing or empty keys disable their capability. Nonempty keys require at least 32 non-whitespace ASCII bytes; configuring identical keys fails startup. Store SHA-256 digests in AppState and compare digests in constant time. Custom server hosts opt in with `AppState::with_headless_keys(headless::ApiKeys::new(...))`. Neither editor sessions nor these keys substitute for one another. Keys grant no admin access, local membership, page mutations, or publication permissions. Rotation/revocation requires changing server configuration and restarting.

All `/api/headless` routes require exactly one `Authorization: Bearer <key>` header. No URL/query key authentication. Missing, malformed, wrong, or disabled keys return 401 with `{error: string}` and `WWW-Authenticate: Bearer`. Responses use `Cache-Control: no-store`. Bearer authentication does not use cookie same-origin checks. No cross-origin browser integration or client-side key storage is supported. Use HTTPS server-side requests and rate-limit at the reverse proxy. The existing public `/api/content` and public site remain available without keys; published content is not confidential.

- `GET /api/headless/pages` and its HEAD use the content key. Returns `[{id, title, slug, template_id, revision}]` from published snapshots, ordered by published slug. Revision is the published page revision. Includes no unpublished drafts or current draft metadata. Reads without the CMS write lock.
- `GET /api/headless/content?slug=/about` and its HEAD use the content key. Same snapshot contract and validation as `/api/content`. Returns `{page, template, components}` or 404 for unpublished. Consumers render `template.regions` in order, preserving block order within each region and resolving definitions by `component_id`.
- `PUT /api/headless/components/{id}` uses only the component key, accepts full Component with matching ID and `renderer:"external"`. IDs use 1–200 ASCII letters, numbers, underscores or hyphens. Creates with 201, or updates an existing external component with 200. Returns Component. Repeated registration retains identity. Cannot replace built-in/CMS-rendered definitions, returning 409. Validates field schema and all affected drafts under the shared database lock; invalid updates roll back. Does not mutate template allowlists, page blocks, published snapshots or reviews. Administrators explicitly allow registered components in template regions before editors can place them. Registration keys can update any external definition, not just those created by the calling app.

Custom components use the existing string field kinds and required flags. No remote renderer scripts, HTML templates, SDK, draft-preview route or publication webhooks. Schema imports/exports include the external renderer through the existing component contract.

## Local serialization

`baddiecore status [directory]`, `baddiecore pull [directory] [--force]` and `baddiecore push [directory] [--force] [--dry-run]` sync components and templates. Content pages are never synced through Git; they move in Content packages. The commands connect directly to the initialized database using `DATABASE_URL`. No HTTP routes or new authentication method. Default directory: `baddiecore-content`.

YAML files have `{schema_version: 1, kind: component | template | page, data: ...}`. Components and templates use the models above. Page data contains only `id`, `title`, `slug`, `aliases`, `template_id`, and `blocks`. Empty aliases are omitted on export; missing aliases import as an empty list. Filenames are `<id>.yaml` for 1–200 ASCII alphanumeric, underscore or hyphen bytes; other IDs use `id.<sha256-of-utf8-id>.yaml`. Git exports group files into `components/` and `templates/`; packages add `pages/`. Preserve array order and sort block field keys. Reject unknown keys, unsupported versions, incorrect filenames, unsafe paths, and files over 4 MiB. `baddiecore.yaml` at the root of a Git export, `{schema_version: 1, kind: export, data: {}}`, marks the directory as an export.

Sync is three-way per export path, such as `templates/homepage.yaml`. Compare SHA-256 hashes of canonical YAML in the database, the files (re-encoded after parsing; malformed files hash raw bytes) and the `sync_base` table, which holds each path's hash when both sides last agreed. Equal database and file hashes are in sync. Otherwise, if the files equal the base, the database changed; if the database equals the base, the files changed; else both changed. Absence is a state, so additions and deletions follow the same rules. Pull and push refuse when any path changed on both sides, unless `--force`. Pull applies database-side changes to files and push applies file-side changes to the database. Each leaves the other side's changes untouched and reports them. `--force` applies every difference toward the target. After success, record the base for every path where both sides agree, and remove base rows for paths absent on both sides. Status reports the classification read-only.

Pull writes the manifest when missing. Before pulling into a directory without one, delete all base rows, because the directory shares no history with the database. Push requires the manifest. Seeding a new database records base rows for the seeded components and templates.

Push runs in one transaction under the database lock. It upserts components, then templates, then deletes templates and components. A definition still allowed by a template or used by a page draft is not deleted; this returns a conflict naming its users and rolls back. Then validate all page drafts. Failure rolls back the entire push; dry run explicitly rolls back even after successful validation. Pull stages all output before atomic per-file renames, but the directory update is not atomic. Unrelated files in item directories are preserved by pull and rejected by push. Neither command loads page data.

## Content packages

Packages move page drafts between installations through the browser, for content that does not belong in Git. A package is a zip of Local serialization files under `components/`, `templates/` and `pages/`, and must contain at least one page. Directory entries, `__MACOSX/` entries and `.DS_Store` files are ignored; any other entry must be a canonical `components/`, `templates/` or `pages/` file. Reject symlink entries, files over 4 MiB, more than 10,000 entries, or 64 MiB unpacked, checking actual rather than declared sizes. Unpack only after the admin check. The upload is bounded by the server's 1 MiB request limit.

Install runs in one locked transaction. Components and templates that already exist are kept unchanged, because Git owns definitions; only missing ones are added. Pages merge by ID and never publish. Import paths are explicit final paths, with no subtree cascade, so pages may swap paths. New pages start at revision 1, changed drafts increment the target revision, identical drafts retain it, and existing published revisions and snapshots are preserved. Validate all resulting drafts and route paths. Any failure, including duplicate paths in the package (400) or a path owned by a different page ID (409), rolls back the whole package.

Security: no raw HTML field rendering, validate URL fields as relative paths or http/https URLs, refuse protocol-relative URLs. Cookie auth mutations require same-origin Origin when present, comparing scheme, host and effective port. Optional `BADDIE_ORIGIN` fixes the browser-facing HTTP(S) origin, without a path. Otherwise the preserved Host header and `BADDIE_SECURE_COOKIE` select the expected origin, HTTPS when true and HTTP otherwise. Forwarded headers are not trusted. Malformed Origin headers are rejected. Production TLS provided by reverse proxy, configurable Secure cookie. Request size limit. Do not log passwords or cookies. Rate-limit `/api/login` at the reverse proxy; per-username throttling is not a substitute for per-client rate limiting.

Authentication is replaceable through `auth::AuthProvider` and `AppState::open_with_auth`. The provider supplies its own state-bound login routes and validates headers into an `Editor { id }`; identity alone grants no CMS permissions. CMS middleware retains same-origin mutation checks and adds Editor to request extensions. `AuthProvider::origin_policy` defaults to the environment settings above; the built-in provider shares its configured policy with CMS middleware. Custom providers may override it with `OriginPolicy::new`. Handlers resolve local membership inside their transaction. Public content does not call the provider. Custom auth routes must enforce their own CSRF checks and keep credentials server-side.

Built-in accounts are keyed by member ID in the `accounts` table, with Argon2id PHC password hashes. Sessions are stored in the `sessions` table by SHA-256 digest of the opaque cookie token, expire twelve hours after sign-in and survive restarts. Deleting an account deletes its sessions. `AppState::open` takes the optional `BADDIE_ADMIN_PASSWORD`: when no admin member has a password, it creates or repairs the `admin` member as an administrator with that password; otherwise it is ignored. Without it, startup fails until an administrator can sign in. `baddiecore reset-admin <username>` makes that member an administrator, adding it if needed, sets its password from a prompt or one stdin line, and ends its sessions. Database CLI access is trusted operator access and bypasses HTTP membership; review comparisons still detect imported content/schema changes. Auth responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
